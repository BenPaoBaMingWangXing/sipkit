## 一句话

用 MoonBit 实现 SIP（RFC 3261）**消息层**的字节级解析、可逐字节还原的重新序列化、以及带字节偏移的结构诊断；正确性以 IETF 官方测试集 **RFC 4475 全部 49 条报文**为外部证据，在**判定、字段、鲁棒性**三个层次上度量，而不是自我声明。

## 要解决的问题

SIP 是所有 VoIP 呼叫、SBC 和 IMS 核心的信令协议。它的解析器有一个特殊处境：**日常被喂敌意输入**。头字段折行、重复的 `Content-Length`、不允许被转义的 `%`、user 部分里混入参数分隔符——这些都是真实网络里每天都在发生的事，也是历史上请求走私与解析歧义漏洞的来源。

MoonBit 生态目前有 WebRTC 媒体栈（`moonbit-community/rtc`）、有 SDP（`coke089/moon-sdp`），但**没有信令层**。对 mooncakes.io 全部 3,243 个模块与 2026 年新建的 1,805 个 MoonBit 仓库做检索，SIP 本体、RFC 3261、torture 测试集三个关键词的命中数均为 0。

结果是：今天在 MoonBit 里无法接收一个 SIP `INVITE`。`sipkit` 补的是这一层，并且只补这一层。

## 技术路径

解析分两层，因为 RFC 4475 本身就把语料分成两类问题：

1. **语法层**（对应 RFC 4475 §3.1.2）：判断一串字节是否构成本消息。失败时给出错误种类与字节偏移。
2. **诊断层**（对应 §3.2 / §3.3）：消息成立，但结构上是否可接受。18 个缺陷码，带偏移与严重级；**只有 error 改变判定，warning 不改变**——这是"代理转发、终端拒绝"这类角色差异能被正确表达的前提。

两层分开的意义在于：把二者混为一谈的 SIP 栈，会拒绝掉本该被转发的消息。

三个工程决定：

- **全程按字节，不构造 `String`。** SIP 是字节协议，头值可能含非 UTF-8 字节。本工具链的 `String` 是 UTF-16（`"sip".to_bytes()` 是 6 个字节而非 3 个），任何一次隐式的字符串化都会在无人察觉时破坏字节协议。
- **`trailing` 保留而非丢弃。** 声明长度之后的字节属于同一数据报里的后续内容。丢掉它会掩盖请求走私面；`parse_message` 暴露它，`to_bytes` 不把它重新粘回去。
- **注释嵌套用深度计数而非递归。** ABNF 允许 `comment` 嵌套，这是典型的栈耗尽向量，实现上限定深度 16。

## 证据的三个层次

评审最该问的问题不是"你做了多少测试"，而是"**你怎么知道它对**"。本项目的证据分三层，每层回答不同的质疑：

### 第一层：判定级——"接受还是拒绝"

| 项目 | 结果 |
|---|---|
| RFC 4475 报文提取 | 49 条，由脚本实现 RFC §2 的 `<allOneLine>` / `<hex>` / `<repeat>` 三种表示法，并处理报文跨页 |
| 有明确判定的向量 | 45 条，**全部与实现一致** |
| 角色相关、不判定的向量 | 4 条（proxy 与 endpoint 期望不同，实现不替调用方猜角色） |
| 逐字节 round-trip | 所有被接受的报文均字节一致；`mpart01` 例外并已文档化 |

关键设计：**报文字节来自 IETF，判定来自 RFC 正文的人工誊抄，实现是唯一被测对象**。从自身实现推导期望值的测试套件无法证明任何事情。

### 第二层：字段级——"解析成了什么"

只断言"接受"是粗的：一个解析器可以接受全部 49 条报文，同时把每个字段都放错位置。RFC 4475 好几节不止说"能否解析"，还**明确写了字段应该是什么**——这些话被逐字做成断言，每条注明章节：

| RFC 原文 | 断言 |
|---|---|
| §3.1.1.9 "the user part is 'user;par=u@example.net'" | user 逐字相等；转义的 `@` 留在 user 里；尾部参数不属于它 |
| §3.1.1.5 "two Contact values, not three" | `C%6Fntact` 是不同的字段名——头名永远不 unescape |
| §3.1.1.4 AOR 不被 `%00` "prematurely shortened" | 解码后 11 字节，NUL 停在下标 5 而不是终止字符串 |
| §3.1.1.2 intmeth | user 到第一个 `:` 为止（`:` 不在 `user-unreserved`），其余是 password |

其中 intmeth 暴露了一个值得记录的规范张力：**RFC 4475 的报文把 `:` 放进了 user 部分，而 RFC 3261 的 ABNF 里 `:` 不是 `user-unreserved`**。两份 RFC 在这里互相打架，实现必须选边——`sipkit` 站 ABNF（`:` 分隔 password），并把理由写进测试注释。评审若复核这两份文档，会发现这不是实现 bug，而是规范自身的裂缝。

### 第三层：鲁棒性——"非法输入会不会把它打崩"

对一个信令解析器，最坏的失败不是拒错，是 **panic**——panic 会带走整条通话路径。

`fuzz_test.mbt` 用五种确定性生成器（可复现，失败能重放）：

| 生成器 | 输入数 | 覆盖面 |
|---|---|---|
| 伪随机字节 | 1,200 | 早期语法出口与错误路径 |
| 结构字节（CR/LF/分隔符/高位） | 1,500 | 敌意空白与分隔符连发 |
| 每条语料报文的截断 | ~294 | 半截报文、未闭合结构 |
| 每条语料报文的单字节变异 | 1,176 | 深层语法与诊断层 |
| 拼接 + 注入 CRLF | ~98 | 分帧边界 |

**4,000+ 输入，零 panic**；同时断言不变量：任何语法错误都带输入内偏移，任何能解析的都能重新序列化。

顺带做了一次减法：负数 `Content-Length` 在语法层已被拒绝，诊断层的 `negative-content-length` 分支因此**永远不可达**——已删除，而不是留着当"防御深度"的装饰。诊断码从 19 收敛到 18。

## 交付边界（明确不做）

本库是 **sans-IO 消息层**，不开 socket、不做 DNS、不持有定时器。

- 不做事务层与对话层：不重传 `INVITE`、不匹配 `ACK`、不计算 `Route` 集。§3.2.1 只作为诊断检查（branch 标识存在）。
- 不做 SDP：`application/sdp` 体按不透明字节返回，`coke089/moon-sdp` 是天然搭配。
- 不做认证：`Authorization` 只作文本解析，无 Digest 计算。
- 不做 TLS/DTLS：属于 `moonbitstack/moontls`。
- 不支持任何 SIP 扩展：`Require` / `Proxy-Require` 任意非空值均报"不支持"，因为本库确实一个都没实现。

## 三个使用场景

**1. 软交换 / SBC 的收包前置检查。**
网关收到 UDP 报文后先过 `analyze`：`syntax-rejected` 直接回 400 且不进入业务状态机；`semantic-rejected` 携带具体缺陷码（如 `multiple-content-length-values`），用于安全告警而不是静默丢弃。字节偏移让日志能直接定位到出问题的那一行。

**2. 呼叫中心话单与信令取证。**
对抓包得到的 SIP 报文批量解析，按 `Call-ID`、`CSeq`、`Via` 的 `branch` 建立呼叫关联。`to_bytes` 的逐字节还原特性保证存档后的报文与线上完全一致，可作为审计证据；`trailing` 字段能暴露"一个 UDP 包里塞了两条消息"这类异常。

**3. 终端 / 浏览器的离线协议教学与测试夹具生成。**
编译到 wasm 后在浏览器里直接解析粘贴的 SIP 报文，实时显示每个头字段的解析结果与诊断；也可作为其他 SIP 实现的对照基准——同一批 RFC 4475 向量喂给两个实现，diff 出差异点。

## 已知限制（如实列出）

1. native 后端未在开发机验证（无 `cl`/`cc`/`gcc`/`clang`），CI 覆盖。
2. `mpart01` 的 `Content-Length: 553` 比 RFC 打印的 hex 体少 14 字节；实现按 `Content-Length` 切分（正确行为）并把余下 14 字节记为 trailing。这是 RFC 文本的问题，不是解析器的问题。
3. **RFC 4475 与 RFC 3261 ABNF 的冲突**：intmeth 的报文把 `:` 放进 user 部分，ABNF 不允许。实现站 ABNF（`:` 分隔 password），代价是该报文的 user 部分比 RFC 叙事暗示的短。
4. **裸 addr-spec 的参数命名空间歧义**：`Contact: sip:a@b;unknownparam` 无尖括号时，`;` 后既是 URI 参数也是 contact 参数，语法上不可分（RFC 3261 §20.10 自己承认并建议总用 `<>`）。实现保证参数可达、user/host 不受影响，但无法承诺它"只"是 contact-param。
5. URI user 部分的 `?` 既是合法字符又是 URI headers 起点。实现以第一个 `@` 作为 userinfo 分隔符；无 userinfo 且 `?`-headers 内含 `@` 的 URI 会被误读，规范对此无正确解。
6. `Reason-Phrase` 的 UTF-8 合法性未校验，仅保留字节。
7. `Date` 只做结构校验（强制 `GMT` 时区 + `HH:MM:SS`），不校验星期与日历一致性。
8. 类型化检查覆盖 `CSeq` / `Max-Forwards` / `Retry-After` / `Via` / `Contact`，其余头字段只做结构检查。

其中第 3、4、5 条不是"还没做完"，而是**规范本身没有正确答案**的问题——实现选择了可辩护的一侧，并把选择写下来。
