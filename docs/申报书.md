## 一句话

用 MoonBit 实现 SIP（RFC 3261）**消息层**的字节级解析、可逐字节还原的重新序列化、以及带字节偏移的结构诊断；正确性以 IETF 官方测试集 **RFC 4475 全部 49 条报文**为外部证据来度量，而不是自我声明。

## 要解决的问题

SIP 是所有 VoIP 呼叫、SBC 和 IMS 核心的信令协议。它的解析器有一个特殊处境：**日常被喂敌意输入**。头字段折行、重复的 `Content-Length`、不允许被转义的 `%`、user 部分里混入参数分隔符——这些都是真实网络里每天都在发生的事，也是历史上请求走私与解析歧义漏洞的来源。

MoonBit 生态目前有 WebRTC 媒体栈（`moonbit-community/rtc`）、有 SDP（`coke089/moon-sdp`），但**没有信令层**。对 mooncakes.io 全部 3,243 个模块与 2026 年新建的 1,805 个 MoonBit 仓库做检索，SIP 本体、RFC 3261、torture 测试集三个关键词的命中数均为 0。

结果是：今天在 MoonBit 里无法接收一个 SIP `INVITE`。`sipkit` 补的是这一层，并且只补这一层。

## 技术路径

解析分两层，因为 RFC 4475 本身就把语料分成两类问题：

1. **语法层**（对应 RFC 4475 §3.1.2）：判断一串字节是否构成本消息。失败时给出错误种类与字节偏移。
2. **诊断层**（对应 §3.2 / §3.3）：消息成立，但结构上是否可接受。18 个缺陷码，带偏移与严重级。

两层分开的意义在于：把二者混为一谈的 SIP 栈，会拒绝掉本该被转发的消息。

三个工程决定：

- **全程按字节，不构造 `String`。** SIP 是字节协议，头值可能含非 UTF-8 字节。本工具链的 `String` 是 UTF-16（`"sip".to_bytes()` 是 6 个字节而非 3 个），任何一次隐式的字符串化都会在无人察觉时破坏字节协议。
- **`trailing` 保留而非丢弃。** 声明长度之后的字节属于同一数据报里的后续内容。丢掉它会掩盖请求走私面；`parse_message` 暴露它，`to_bytes` 不把它重新粘回去。
- **注释嵌套用深度计数而非递归。** ABNF 允许 `comment` 嵌套，这是典型的栈耗尽向量，实现上限定深度 16。

## 外部一致性证据

证据由脚本从 RFC 原文机械生成，不手写：

| 项目 | 结果 |
|---|---|
| RFC 4475 报文提取 | 49 条，实现 RFC §2 的 `<allOneLine>` / `<hex>` / `<repeat>` 三种表示法，并处理报文跨页 |
| 有明确判定的向量 | 45 条，**全部与实现一致** |
| 角色相关、不判定的向量 | 4 条（proxy 与 endpoint 期望不同，实现不替调用方猜角色） |
| 逐字节 round-trip | 所有被接受的报文均字节一致；`mpart01` 例外并已文档化 |
| 测试后端 | wasm / wasm-gc / js 本地全通过；native 由 CI 覆盖（开发机无 C 编译器） |
| 鲁棒性 | 随机字节 + 结构字节 + 截断 + 单字节变异 + 拼接，共 4000+ 输入，**零 panic** |
| 测试规模 | 71 个测试；`moon coverage analyze` 显示库内 50 行未覆盖 / 1698 可执行行（约 97%） |

关键设计：**报文字节来自 IETF，判定来自 RFC 正文的人工誊抄，实现是唯一被测对象**。从自身实现推导期望值的测试套件无法证明任何事情。

两个常被实现反了的用例：

- §3.1.1.6 `lwsdisp`：`caller<` 之间没有空白，语法禁止，但 RFC 明确指出这是规范 bug 并要求接受。本实现接受。
- §3.1.1.5 `esc02`：`%` 并非处处是转义。`C%6Fntact` **不是** `Contact`，`branch=z9hG4bK209%fzsnel234` 是合法值。本实现按字面比较头名，并接受游离的 `%`。

## 交付边界（明确不做）

本库是 **sans-IO 消息层**，不开 socket、不做 DNS、不持有定时器。

- 不做事务层与对话层：不重传 `INVITE`、不匹配 `ACK`、不计算 `Route` 集。§3.2.1 只作为诊断检查（branch 标识存在）。
- 不做 SDP：`application/sdp` 体按不透明字节返回，`coke089/moon-sdp` 是天然搭配。
- 不做认证：`Authorization` 只作文本解析，无 Digest 计算。
- 不做 TLS/DTLS：属于 `moonbitstack/moontls`。
- 不支持任何 SIP 扩展：`Require` / `Proxy-Require` 任意非空值均报"不支持"，因为本库确实一个都没实现。

## 三个使用场景

**1. 软交换 / SBC 的收包前置检查。**
网关收到 UDP 报文后先过 `analyze`：`syntax-rejected` 直接回 400 且不进入业务状态机；`semantic-rejected` 携带具体缺陷码（如 `multiple-content-length-values`），用于安全告警而不是静默丢弃。字节偏移让日志能直接定位到出问题的那一行。

**2. 呼叫中心话单与信令取证。**
对抓包得到的 SIP 报文批量解析，按 `Call-ID`、`CSeq`、`Via` 的 `branch` 建立呼叫关联。`to_bytes` 的逐字节还原特性保证存档后的报文与线上完全一致，可作为审计证据；`trailing` 字段能暴露"一个 UDP 包里塞了两条消息"这类异常。

**3. 终端 / 浏览器的离线协议教学与测试夹具生成。**
编译到 wasm 后在浏览器里直接解析粘贴的 SIP 报文，实时显示每个头字段的解析结果与诊断；也可作为其他 SIP 实现的对照基准——同一批 RFC 4475 向量喂给两个实现，diff 出差异点。

## 已知限制（如实列出）

1. native 后端未在开发机验证（无 `cl`/`cc`/`gcc`/`clang`），CI 覆盖。
2. `mpart01` 的 `Content-Length: 553` 比 RFC 打印的 hex 体少 14 字节；实现按 `Content-Length` 切分（正确行为）并把余下 14 字节记为 trailing。这是 RFC 文本的问题，不是解析器的问题。
3. URI user 部分内的 `?` 在语法上本身有歧义（`?` 既是 user 合法字符，又是 URI headers 起点）。实现以第一个 `@` 作为 userinfo 分隔符，这正是 §3.1.1.2 能解析的原因；无 userinfo 且 `?`-headers 内含 `@` 的 URI 会被误读，规范对此无正确解。
4. `Reason-Phrase` 的 UTF-8 合法性未校验，仅保留字节。
5. `Date` 只做结构校验（强制 `GMT` 时区 + `HH:MM:SS`），不校验星期与日历一致性。
6. 类型化检查覆盖 `CSeq` / `Max-Forwards` / `Retry-After` / `Via` / `Contact`，其余头字段只做结构检查。
